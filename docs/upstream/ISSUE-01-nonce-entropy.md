## Title

`OID4VP nonce is a base64-encoded timestamp, not a random value (inji-verify-sdk)`

## Body

### What we found

The `nonce` in Inji Verify's OID4VP authorisation requests is a base64-encoded
millisecond timestamp rather than a random value. Because it is derived from the clock,
it is predictable to within a few hundred milliseconds.

The nonce exists to tie a wallet's response to one specific request, so that an old
response cannot be replayed against a new one. A predictable nonce weakens that
protection.

We also found a second, smaller problem in the same place: the value is encoded with
standard base64, which can contain `=`. That character is not safe to put in a URL
without escaping, and the nonce does travel in a URL.

Both come from the same one-line function, so one change fixes both.

### Where it comes from

`inji-verify-sdk/src/utils/api.ts`, lines 10–12:

```ts
const generateNonce = (): string => {
  return btoa(Date.now().toString());
};
```

`Date.now()` is the current clock. `btoa` is standard base64, which pads with `=`.

This function is used at `api.ts:89` and `api.ts:159`, and the SDK is what the UI uses
(`verify-ui/package.json` depends on `@injistack/react-inji-verify-sdk` 0.18.1). So the
nonce that ends up in the authorisation request is the one the SDK made.

### Worth noting: the service already does this correctly

`verify-service` has a proper implementation in
`verify-service/src/main/java/io/inji/verify/utils/SecurityUtils.java`, which uses
`SecureRandom` over 16 bytes.

But in `VerifiablePresentationRequestServiceImpl.java:86` it is only a fallback:

```java
String nonce = vpRequestCreate.getNonce() != null
    ? vpRequestCreate.getNonce()
    : SecurityUtils.generateNonce();
```

Because the SDK always sends a nonce, the good generator never runs in the normal flow.
**So this is not a missing capability — it is a correct implementation being overridden
by its caller.** We think that makes it a small fix rather than a design change.

### How we confirmed it

Run against Inji Verify 0.18.2 using the OpenID Foundation conformance suite 5.3.1
(OID4VP 1.0 Final, verifier alpha tests). The suite flagged it on its own, without us
looking for it:

```
VP1FinalEnsureMinimumNonceEntropy — WARNING
"Nonce does not appear to have sufficient entropy (calculated Shannon entropy is below
the threshold). Section 5.2 of OID4VP 1.0 Final requires the nonce to be a 'fresh,
cryptographically random number with sufficient entropy'."
actual: 73.68    expected: 96.0
```

```
CheckForInvalidCharsInNonce — FAILURE
"Non URL safe characters found in nonce. This may introduce interoperability issues."
invalid_chars: ["="]
```

We decoded three nonces from two different request paths. Each one was the timestamp of
the moment it was made:

| nonce | decodes to | gap from the request's own `issuedAt` |
|---|---|---|
| `MTc4OTg4MzIxMzQ5MA==` | 1789883213490 | — |
| `MTc4OTg4NDUzNjY3OQ==` | 1789884536679 | 120 ms |
| `MTc4OTg4NDY1NjQzNg==` | 1789884656436 | 158 ms |

Signed conformance suite logs are available if useful — test ID `MtzpWoD2dVgtic0`.

### Suggested fix

Use the browser's random number generator and an encoding that is safe in URLs:

```ts
const generateNonce = (): string => {
  const bytes = new Uint8Array(32);
  crypto.getRandomValues(bytes);
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, "-")
    .replace(/\//g, "_")
    .replace(/=+$/, "");
};
```

32 bytes gives 256 bits, comfortably above the 128 bits the spec discussion recommends.
Stripping the padding and swapping the two characters makes it URL-safe, which covers the
second problem.

`crypto.getRandomValues` is available in every browser the UI supports and in Node 18+.

### How to reproduce

1. Start Inji Verify and request any credential from the UI.
2. Look at the `/v1/verify/vp-session-request` response in the browser's network panel.
3. Base64-decode the `nonce`. It will be the current time in milliseconds.
4. Repeat — each new nonce is the new current time.

### Context

We are a team working on MOSIP Decode 2026, building automated conformance testing for
Inji Certify and Inji Verify against the OpenID Foundation suite. Happy to supply the
signed logs or test anything you would like checked.

## Notes for us (not part of the issue)

- **This corrects our own earlier root-cause guess.** The Day 1 findings said the nonce
  was generated by Inji Verify generally. The service is fine; the SDK is the source. The
  report is far more actionable for the maintainer as a result, and it is a good example
  of why the "read the source, don't guess" rule earns its place.
- F-01 and F-02 are combined into one issue deliberately. They share a root cause and one
  fix; filing two issues would create two conversations about one three-line change.
- Tone is deliberately plain. The maintainer may not have the conformance suite in front
  of them, so every claim is either quoted from their own code or from the suite's output.
- The suggested fix is offered, not insisted on. If they would rather have the SDK stop
  sending a nonce entirely and let `SecurityUtils.generateNonce()` handle it, that is
  arguably cleaner — worth mentioning in the thread if they engage.
